# 정답 코드 실행 검증 켜기 (INTAKE_EXEC)

AI 가 쓴 정답 코드를 서버에서 실제로 돌려 `test_cases` 의 기대 출력과 비교한다. 켜면 **틀린 출력·틀린 정답은 등록 전에 자동으로 막히고**,
실행이 맞고 확인필요가 없는 코딩·디버깅 문제는 승인 없이 자동 등록된다. 꺼져 있으면 코딩·디버깅 문제는 전부 사람 승인 대기가 된다.

> 이 문서의 절차는 **이 개발 PC(Windows, Docker 없음)에서는 시험하지 못했다.** 배포 환경에서 아래 3번 점검을 먼저 통과시킨 뒤 켠다.

## 1. 켜는 조건 (코드에 이미 구현됨)
두 값이 **모두** 있어야 켜진다. 한쪽만 있으면 꺼진 채로 두고 시작 로그에 경고를 남긴다.
```
INTAKE_EXEC=on             # 실행 검증 사용
INTAKE_EXEC_ISOLATED=on    # 운영자가 "격리된 환경에서 돌고 있다"고 확인했다는 표시
```
- 리눅스에서는 실행 때마다 `unshare -rn` 으로 네트워크를 끊는다. **끊을 수 없으면 실행하지 않고** 해당 문제를 사람 승인으로 보낸다(안전한 쪽).
- 컨테이너가 이미 네트워크를 막았다면 `INTAKE_EXEC_NO_NET=off` 로 이 단계를 건너뛸 수 있다(컨테이너가 정말 막았을 때만).
- 코드 실행 제한: CPU 5초, 메모리 512MB, 파일 쓰기 1MB, 프로세스 생성 금지(리눅스). 서버 환경변수(키 등)는 자식 프로세스에 넘기지 않는다.
- C/C++ 소스의 서버 파일 읽기 지시(따옴표·절대경로 include, `#embed`, `.incbin`)는 컴파일 전에 막는다.

## 2. 구조적 주의: API 서버 안에서 돌리면 격리가 약하다
현재 구현은 **API 서버 프로세스가 직접 하위 프로세스로 코드를 실행**한다. 그런데 API 서버는 DB·AI API 와 통신해야 해서 컨테이너 전체를 `--network none` 으로 막을 수 없다.
그래서 네트워크 차단을 `unshare -rn`(사용자 네임스페이스) 에 의존하는데, 도커 기본 설정(seccomp)은 이를 막는 경우가 많다.

| 방법 | 내용 | 장단점 |
|---|---|---|
| **1. 임시: 같은 컨테이너에서 `unshare` 허용** | 컨테이너에 사용자 네임스페이스를 허용하는 seccomp 설정을 준다 | 바로 가능하지만 컨테이너 권한을 넓히는 것이라 격리가 약해진다. 비루트, 읽기 전용 파일시스템, `--cap-drop ALL`, `--pids-limit`, `--memory` 를 함께 준다 |
| **2. 권장: 별도 실행 서비스** | 네트워크가 없고 읽기 전용인 전용 컨테이너가 코드를 받아 돌리고 결과만 돌려준다 | 격리가 가장 확실하다. **지금 코드에는 없고 만들어야 한다**(`checker.run_code` 를 원격 호출로 바꾸는 작업). 기존에 코드 실행용 서비스가 있으면(`docker-compose-dev.yml` 에 `runner_service` 라는 이름이 보임, 내용은 확인하지 않음) 재사용을 검토 |

방법 2 로 가려면 어떤 실행 서비스를 쓸지(기존 것 재사용 또는 신규)를 먼저 정해야 한다.

## 3. 켜기 전 점검 (배포 환경에서)
```
cd noti_test
python check_exec_isolation.py
```
- 모의 점검(A)과 리눅스 실제 점검(B)이 모두 `PASS` 여야 한다. 특히 B 의 `unshare 사용 가능`, `네트워크(루프백 포함) 차단`, `프로세스 생성 제한`, `메모리 제한`.
- `unshare 사용 가능` 이 FAIL 이면 방법 1 의 권한을 확인하거나 방법 2 로 간다. 이 상태에서 켜도 실행은 거부되어 승인 대기로 가므로 위험하지는 않지만 자동 등록은 늘지 않는다.
- `프로세스 생성 제한` 은 실행 UID 에 따라 달라질 수 있으니 반드시 배포 환경에서 확인한다.

## 4. 켠 뒤 확인
1. 실제 문제지 몇 개를 올려 `GET /intake/jobs/{id}/items` 에서 상태를 본다.
   - 실행이 맞고 확인필요가 없는 코딩 문제 → `registered`(자동 등록)
   - 기대 출력이 틀린 문제 → `blocked`(`check_fails` 에 `exec: …`)
   - 실행 환경이 없는 언어(java 등) → `needs_review`("실행해 확인하지 못했습니다")
2. 틀린 출력이 실제로 막히는지, 정상 문제가 자동 등록되는지 둘 다 본다.

## 5. 정책 ("보통")
실행 검증이 통과하고 `확인필요` 가 없으면 자동 등록한다. **AI 가 직접 채운 정답코드도 실행이 맞으면 자동 등록**한다.
`참고` 항목은 승인에 영향을 주지 않는다. 이 동작은 `noti_test/test_policy.py` 가 고정한다.
