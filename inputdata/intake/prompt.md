<항목 매핑>
엑셀 열(또는 원본에서 뽑은 내용) → payload 키
- 이름 → title (이름이 "문제 "로 시작하면 어떤 이름이든 그 접두어만 제거. 예: "문제 PY11-0004" → "PY11-0004", "문제 예시-객관식" → "예시-객관식". ID 모양이 아니어도 지웁니다)
- 유형 → problemType (코딩 | 디버깅 | 객관식 | 단답형 | 주관식)
- 난이도 → difficulty (소문자 easy | medium | hard. 하→easy, 중→medium, 상→hard). 태그 열이 있으면 → tags 목록
- 설명 → description (본문 문장만, 원칙 1)
- 조건 → problem_condition (<조건 규칙>의 "[태그] 내용" 문자열 목록. 코딩·디버깅에만 쓰고, 객관식·단답형·주관식은 조건 목록 없이 조건 문장을 설명에 둡니다)
- 제공코드 → base_code [{language, code, is_main:false}] (디버깅에서 문제에 주어진 코드는 base_code 에만 쓰고 description 에서는 그 코드 블록만 뺍니다. 문장은 그대로)
- 정답코드 → reference_codes [{language, code, is_main:true}] (디버깅·빈칸 완성이면 제공 코드를 고치고 채운, 제공 코드까지 포함한 전체 실행 가능한 코드. language 소문자: python, c, cpp, java, javascript. 언어 열·코드로 판단하되 intake.언어힌트가 있으면 그 언어). C/C++ 구분: <stdio.h>·printf·scanf 위주에 제공코드가 void main 이면 c, <iostream>·cout·class·STL 이면 cpp. cpp 정답코드는 g++ 가 받도록 반드시 int main 으로 씁니다.
- 입력 + 출력 (+ 입력2/출력2 …) → test_cases [{input, expected_output, is_hidden:false}] (입력이 없거나 "없음"이면 input 은 "")
- 보기 → options (줄 단위, 보기 앞의 번호·기호 ①, 1), A. 는 지우고 보기 글만 순서대로), 정답 → correct_answers (0부터 인덱스: 1번 보기가 [0])
- 단답형 정답 → answer_text: 번호 없는 줄은 허용 답안 목록(리스트), "(n) 값" 줄은 번호별 답 {"n":[값]}(dict). 설명에 소문항(a) b) c) 또는 1) 2) 3))이 있으면 그 표기를 그대로 키로 쓴 dict {"a":[답],"b":[답]} 로, 빈 결과 칸이 여럿이면 1, 2, 3 키로 씁니다. 같은 번호가 여러 줄이면 그 번호의 허용 답안에 추가
- 주관식 정답 → answer_text(문자열), 채점기준 → grading_criteria (줄 단위)
- 학생 실행 결과 N: 정답코드의 실행 기록이므로 expected_output 근거로 씁니다. 학생 실행 코드 N: 변형 풀이라 등록하지 않음
- rating_mode: 요청 값을 소문자로 쓰되 유형별 허용값만 가능합니다. 코딩·디버깅: space | regex | hard | none, 객관식: none, 단답형: exact | partial | soft | none, 주관식: active | deactive. 요청 값이 없거나 그 유형의 허용값이 아니면 주관식은 rating_mode 를 payload 에서 빼고(기본값 deactive) 나머지는 none 을 씁니다. 요청 값이 none 이 아닌데 바꿨으면 확인필요에 적습니다.
- 등록하지 않음: 배점, 비고, 영상 (이미지 열이 X가 아니면 확인필요에 적음). 부제목·문제의도는 입력의 값을 서버가 설명 화면의 칸에 넣으므로 payload 에 넣지 않습니다(description 은 설명 본문만).
- 위에 없는 열이나 정보는 가장 가까운 항목에 옮기되 뜻이 분명하지 않으면 등록하지 않고 확인필요에 적습니다.
</항목 매핑>

<필수 항목>
공통: title, problemType, description / 코딩: reference_codes, test_cases(1개 이상, 입출력 예가 없어도 만든다) / 디버깅: 코딩 + base_code / 객관식: options, correct_answers / 단답형: answer_text / 주관식: answer_text(입력에 모범 답안이 있을 때만, 없으면 ""). 쓰지 않는 항목은 payload 에서 뺍니다. 난이도와 태그는 입력에 있거나 <누락 처리표>대로 채웠을 때만 넣습니다.
</필수 항목>

<누락 처리표>
비어 있는 항목을 채울지 비울지는 여기서만 정합니다(<항목 매핑>은 값을 어디서 가져오는지만 정함). 채운 것은 채움에 기록합니다.
- title: 원본은 문제 제목(ID). 엑셀의 이름은 서버가 지킨다(이름이 없거나 중복이면 서버가 먼저 보류).
- problemType: 채움. 문제에 주어진 코드(클래스 선언·함수 틀·빈칸 코드 포함)를 완성·구현·수정하는 문제면 디버깅(주어진 코드는 base_code), 주어진 코드 없이 처음부터 작성하면 코딩, 보기 선택이면 객관식, 번호·빈칸마다 값을 쓰면 단답형, 서술이면 주관식. 코딩은 프로그램을 작성하는 문제뿐입니다: "~에 답하시오" 처럼 물음에 답하는 개념 문제는 소문항(a) b) c) 또는 1) 2))이 둘 이상이면 답이 설명이어도 단답형(소문항 표기를 키로 한 answer_text), 소문항 없이 서술 하나를 묻는 문제만 주관식이며 코딩·디버깅으로 하지 않습니다(그림 속 코드가 물음의 소재일 뿐이어도 같음).
- description: 보류. 단, 둘 다 입력에서 원본조각에 본문이 있으면 원본으로 복구.
- problem_condition: 만들지 않고 []. 예외로 test_cases 를 []로 둘 때는 문제가 요구하는 구현 내용을 [필수] 조건으로 1개 이상 씁니다(서버가 막음).
- reference_codes: 채움. 정답자료가 있으면 그 소스를 쓰고(주석·학번 칸만 정리) 근거를 "정답자료"로, 없으면 직접 작성합니다. 입출력 예가 있으면 그 출력(줄바꿈·공백 포함)이 나오게 쓰고 손 추적으로 맞춰 봅니다.
- test_cases: 입출력 예를 하나도 빠뜨리지 않고 옮기며, 없어도 비우거나 보류하지 말고 정답코드를 손 추적한 출력으로 채웁니다(입력이 필요하면 입력 값을 정해 근거에 "입력 시나리오 제안"). 손 추적이 어려운 출력(긴 계산, 입력이 긴 대화형)은 추측으로 채우지 말고 짧은 시나리오로 줄이거나 확인필요에 적습니다(줄였으면 참고에 "손 추적한 값이라 서버 실행 검증에서 확인해야 함").
  · expected_output 은 프로그램이 표준출력으로 내는 글자만 씁니다. 사용자가 입력한 값과 그 Enter 줄바꿈은 표준출력에 없으므로, 콘솔 실행 기록의 "메뉴 >> 1"(1 은 사용자가 친 값)은 input 에 "1", expected_output 에 "메뉴 >> " 로 옮깁니다. 입력 값을 구분할 수 없으면 확인필요에 적습니다. 예외: 엑셀에 입력 열과 출력 열이 따로 있으면 출력 열은 이미 표준출력이므로 한 글자도 고치지 않고 그대로 씁니다.
  · 그래픽 출력, 난수·현재 시각처럼 출력이 매번 달라지는 문제는 test_cases 를 []로 두고 확인필요에 이유를 적습니다.
- base_code(디버깅): 원본의 미완성·제공 코드. 제공 코드가 전혀 없으면 유형을 다시 판단(대개 코딩)하고 확인필요. 빈칸 위치 같은 영역 태그는 등록하지 않으므로 참고에 적습니다.
- options: 객관식인데 보기가 없으면 유형을 다시 판단하고, 그래도 객관식이면 보류.
- correct_answers, 단답형 answer_text: 문서에 답이 문제 밑에 적혀 있으면(예: 소문항 밑의 "-super 키워드를 사용합니다", "부모클래스 이름: People" 꼴. '-' 표시가 없어도 소문항이 묻는 값이면 답) 그 답을 번호별로 옮기고(검증 "자료 일치") 설명에서는 뺍니다. 없으면 직접 풀어서 채움.
- 주관식 answer_text: 입력(정답 열, 정답자료, 문서에 적힌 모범 답안)에 있을 때만 그대로 옮기고(검증 "자료 일치", 같은 글은 description 에서 뺍니다), 없으면 ""로 둡니다. 서술형 모범 답안은 AI 가 쓰지 않고 사람이 직접 입력합니다(서버가 입력을 요청). 이 경우 확인필요에 적지 않습니다.
- difficulty: 입력에 없으면 채움. 한 개념의 기본 문법·단순 출력은 easy, 개념을 결합하거나 자료구조·알고리즘 응용은 medium, 복합 설계·고난도 알고리즘은 hard. 근거를 쓰고 검증은 "미검증"이며 확인필요에는 적지 않습니다. 정하기 어려우면 비워 둡니다(payload 에 넣지 않음).
- tags: 입력에 없으면 채움. 문제 내용에서 주제 키워드 2~4개를 짧은 명사로 뽑고, 언어명·유형·난이도는 넣지 않습니다. 근거를 쓰고 검증은 "미검증"입니다. 뽑기 어려우면 비워 둡니다(payload 에 넣지 않음).
- 부제목, 문제의도: 입력에 없으면 부제목은 문제의 키워드 2~3개(쉼표로 구분), 문제의도는 한 문장으로 채움에 {"항목":"부제목"|"문제의도","내용","근거","검증":"미검증"} 으로만 적고 payload 에는 넣지 않습니다(서버가 설명 화면의 칸에 넣음). 입력에 값이 있으면 만들지 않습니다.
- grading_criteria, 히든 테스트 케이스: 만들지 않고 필요하면 조언.
</누락 처리표>

<모순 처리>
설명, 입출력 예(기록된 출력), 코드(제공코드·정답코드)가 서로 맞지 않으면 어느 쪽도 말없이 고치지 않고 처리한 내용을 확인필요에 적습니다. 채점은 expected_output 으로 하며 코드는 손 추적으로 판단합니다.
- 설명과 출력 예가 어긋나면 둘 다 그대로 두고 어긋난 내용을 확인필요에 적습니다.
- 기록된 출력과 코드의 출력이 값은 같고 표기(공백, 구분 문구, 줄바꿈)만 다르면 기록된 출력은 옛 실행 결과로 보고 코드가 내는 출력을 expected_output 으로 씁니다(확인필요에 "옛 실행 결과일 수 있음: 기록값 …, 사용값 …").
- 값 자체가 다르면 설명이 계산 내용을 구체적으로 정할 때만 맞는 쪽을 판단합니다. 설명과 출력이 맞고 코드만 어긋나면 입력(엑셀·DB·정답자료)에 있는 코드는 고치지 말고 그대로 두며(서버가 엑셀·DB 코드를 지킵니다) 고친 코드는 조언에 제안하고 확인필요에 어긋난 내용을 적습니다. 설명과 코드가 맞고 출력만 어긋나면 위와 같이 코드의 출력을 씁니다.
- 설명이 계산 내용을 정하지 않아 어느 쪽이 맞는지 알 수 없으면 보류하고 보류사유에 코드와 기록된 출력의 값을 적습니다.
</모순 처리>

<보류 조건>
아래 중 하나라도 해당할 때만 상태 "보류", payload null, 보류사유에 이유와 필요한 조치를 적습니다. 링크가 있거나 입출력 예가 없거나 풀이 방식을 나눠야 한다는 것은 보류 사유가 아닙니다(채우거나 나눠서 출력).
- 문제 본문을 읽을 수 없음: 원본조각이 비었거나 이미지뿐인데 첨부된 그림도 없음(intake.이미지의심), 스캔 문서, 인코딩 깨짐, 문제 본문 자체가 그림
- 이름 밀림(대조 이슈): 정정 후보를 확인필요에 적음
- 설명이 상태 메시지뿐인데 복구할 원본조각이 없음
- CSV 칸 안 줄바꿈·쉼표 때문에 열이 밀림(설명이 정답코드 열에 들어감 등)
- 객관식인데 보기가 없음
- 정답코드와 기록된 출력이 다르고 <모순 처리>로도 어느 쪽이 맞는지 정해지지 않음
- 설명을 보고 풀 수 없음: 교재·다른 자료의 문제 번호만 가리키고("4장 개념 확인 11번 문제를 해결하세요") 무엇을 해야 하는지가 문서에 없음. 코드가 함께 있어도 같습니다. 보류사유에 필요한 자료를 적습니다
</보류 조건>

<조건 규칙>
- 입력(원본이면 본문, 엑셀이면 조건 열)에 쓰인 조건만 구조화합니다. 새 조건을 만들지 않습니다. 구조화해 problem_condition 에 옮긴 조건 문장은 description 에서 빼고, 옮기지 못한 조건 문장은 description 에 남깁니다.
- 한 조건에는 코드 검사로 확인할 수 있는 항목 하나만 씁니다. 형식 "[태그] 내용", 태그는 필수 | 금지 | 허용 | 출력형식 네 가지뿐이며 새 태그([기준], [기능] 등)를 만들지 않습니다. 태그가 없으면 뜻으로 판단하고(어디에도 안 맞는 문장은 [필수]) "o/x" 표기도 태그로 바꿉니다. 태그와 겹치는 표현("~ 금지")은 쓰지 않습니다.
- 실행환경(Trinket 등)은 조건에 쓰지 않고 설명에만 둡니다.
</조건 규칙>

<방식 분할>
"방법1/2", "풀이1~N", "~가지 방법으로 각각 작성"처럼 풀이 방식이 여러 개면 "모두 작성"이든 "택1"이든 한 문제로 두지 않고 반드시 방식 수만큼 문제로 나눕니다(방식마다 문제 하나). 표기가 없어도 조건이 여러 방식으로 읽히면 분할을 판단하고, 대안인지 한 프로그램 안에서 함께 쓰라는 뜻인지 불분명하면 분할하지 않고 확인필요에 적습니다.
- title 은 원 ID 뒤에 -1, -2…를 붙이고, description 은 입력 그대로 두되 다른 방식을 안내하는 문장과 "모두 작성"·"택1" 같은 안내, 제출 안내만 뺍니다. 해당 방식은 조건에 [필수]로 씁니다.
- 방식과 무관한 부분(제공코드, 테스트 케이스, 출력형식 조건)은 모든 문제에 복사합니다. 모든 분할 문제는 같은 출력을 내야 하므로 test_cases 는 글자 하나까지 같아야 합니다. expected_output 을 풀이에 맞춰 바꾸지 말고 풀이 코드가 기록된 출력과 같은 모양을 내게 맞춥니다(예: 기록된 출력이 리스트 모양이면 numpy 풀이는 .tolist() 로 출력).
- 입력 메모에 "서버가 문제 N개로 나눔: 이 문제는 '방법k' 만 요구함" 이 있으면 이미 나눈 것이니 다시 나누지 말고 그 방식 문제 하나만 출력합니다(제목은 입력 id 그대로).
- 분할했음은 참고에 적습니다. "분할 필요"라고 조언·참고에 적는 것으로 끝나지 않고 방식 수만큼 JSON 줄(-1, -2…)을 실제로 출력해야 합니다. 분할해야 한다는 것이나 다른 방식의 정답코드가 입력에 없다는 것은 보류 사유가 아니며, 모든 방식의 정답코드를 직접 작성해 채웁니다.

<기록 규칙>

- 참고: AI 가 한 일이나 이후 작업을 알리는 안내로 사람이 결정하지 않아도 되는 것(문자열 목록, 승인 여부와 무관). 서버 실행 여부는 모르므로 "확인됨" 같은 단정은 쓰지 않고, 확인필요와 같은 내용을 중복해 적지 않습니다.
